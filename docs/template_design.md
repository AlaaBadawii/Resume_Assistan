# Resume Template Design — `templates/resume_template.docx`

Generated by `src/build_template.py`. Re-run that script to regenerate the
template; do not hand-edit the DOCX.

## Design decisions

### Layout
- **Single column, A4 page by default (210 × 297 mm), ~0.7–0.8 in margins.**
  A4 is the default because the primary target market is Egypt; US Letter
  (8.5 × 11 in) is available via `build(output_path, page_size="Letter")` or
  `python src/build_template.py --page-size Letter`. Unsupported page sizes
  are rejected with a `ValueError` listing the supported values.
  ATS parsers and Word both handle linear top-to-bottom reading order
  reliably.
- **No tables, text boxes, drawings, or embedded media.** All structure is
  expressed with named paragraph styles so the future generator can address
  content programmatically and ATS extractors see plain paragraphs.
- **Empty Word header and footer.** Contact details live in the document body
  (first paragraphs), because many parsers ignore header/footer content and
  some strip it entirely.
- **Centered header block** (name → target title → specialty/tech line →
  contact line), left-aligned body. Section headings use a thin bottom rule —
  a paragraph border, which is ATS-safe (it is not an image).
- **One-page default** with headroom: the blank template occupies well under
  one page, so a filled resume starts at one page and can spill to a second
  page only when the selected content justifies it.

### Typography
- Calibri throughout (same family the Master Resume uses).
- Sizes: name 20 pt · section heading 12 pt · body/bullets 10.5 pt ·
  meta/contact 9.5 pt.
- Emphasis comes from style properties (bold/italic/color), never from
  ad-hoc run formatting.

## Available Word styles

| Style name | Role |
|---|---|
| `Resume Name` | Candidate name (header block) |
| `Resume Title` | Target professional title |
| `Resume Tagline` | Specialty/focus + 2–3 key technologies |
| `Resume Contact` | Phone, email, portfolio, LinkedIn, GitHub, location |
| `Resume Section Heading` | Top-level section (blue, bold, bottom rule) |
| `Resume Subheading` | Category inside a section (e.g., skill groups) |
| `Resume Project Title` | Project title |
| `Resume Job Title` | Job/role title (also reused for degree line) |
| `Resume Entry Meta` | Dates, organizations, repositories — italic support line |
| `Resume Body` | Prose paragraphs and flat entry lines |
| `List Bullet` | Built-in Word bullet style for all bullet content |

All custom styles except `Resume Section Heading` derive from `Normal`.
`Resume Section Heading` keeps its custom name but derives from Word's
built-in **`Heading 1`** style, so section headings carry real semantic
heading hierarchy (outline level 1 for navigation panes, TOC generation, and
accessible document structure) while the resume-specific formatting (12 pt,
bold, `#1F3B57`, bottom rule, spacing, `keep_with_next`) is applied on top of
the inheritance. Section headings additionally carry `keep_with_next` so a
heading never strands alone at a page bottom.

`Resume Project Title` and `Resume Job Title` look identical by design
(same size/weight) but are **distinct style names**, so the generator can
tell projects from jobs without parsing text.

## Placeholder conventions

- Every replaceable unit is a token: `[UPPER_SNAKE_CASE]`.
- Tokens are **coarse-grained** — one token per logical field
  (`[PROJECT_TITLE_1]`, `[SUMMARY_PARAGRAPH]`), not per word.
- Index suffixes (`_1`, `_2`) mark repeated structures; the generator may
  clone the surrounding paragraphs and increment indices.
- Scaffolding characters that are *not* placeholders (the `|` separators,
  the `—` in certification lines) are literal layout text.
- The blank template intentionally contains no realistic sample values so
  that no candidate-specific claim can leak into a generated document by
  accident.

## Example slots are not content limits

The blank template ships with a small, fixed number of *visual example
slots* so the layout can be inspected at a glance:

| Slot group | Example count in the blank template |
|---|---|
| Projects | 2 (`[PROJECT_TITLE_1]`, `[PROJECT_TITLE_2]`) |
| Experience entries | 2 (`[JOB_TITLE_1]`, `[JOB_TITLE_2]`) |
| Skill categories | 3 (`[SKILL_CATEGORY_1..3]`) |
| Certifications | 2 (`[CERTIFICATION_TITLE_1..2]`) |
| Languages | 2 (`[LANGUAGE_1..2]`) |

These counts are **illustrative only — they are not maximum content limits**.
The future resume renderer must dynamically create and remove paragraphs
using the named styles above (clone the paragraph carrying the style, fill
its placeholders, delete surplus paragraphs) to match the candidate's actual
evidence. The architecture must never hardcode a maximum number of projects,
experience entries, certifications, skill categories, or languages.

## Dynamic section ordering (future)

Sections are contiguous paragraph blocks delimited by paragraphs styled
`Resume Section Heading`. To render for a target role:

1. Split the document body into blocks: each block starts at a
   `Resume Section Heading` and ends before the next one (the header block is
   the block before the first heading).
2. Order the blocks according to the role's section plan (e.g., put
   `EXPERIENCE` before `SELECTED PROJECTS` for a senior IC role).
3. Drop blocks with no verified content to fill them.
4. Re-emit paragraphs in the new order (python-docx
   `paragraph._element.addnext(...)`), then fill placeholders from the
   Master Resume evidence store.

Nothing in the template hard-codes the current order — order is data, not
formatting.

## Limitations discovered

- **PDF preview is approximate — not a Word-faithful renderer.**
  LibreOffice/Word are unavailable in this environment, so
  `tests/render_template_pdf.py` maps styles to CSS and renders with
  WeasyPrint. It is good enough to confirm hierarchy, spacing, and one-page
  fit, but it does **not** verify actual Word or LibreOffice rendering and is
  not pixel-faithful to Word. Bullet glyphs and fonts may differ slightly in
  real Word. The preview reads the real page size and margins from the DOCX
  section (so an A4 template previews as A4) and writes to the intended
  filename `output/resume_template_preview.pdf` (path built with `pathlib`).
- **Bullets use the built-in `List Bullet` style** rather than a custom
  `Resume Bullet` style, because converters and ATS tools reliably recognize
  the built-in name; a renamed custom style risks being read as plain text.
- **Second page is not pre-verified with real content** — overflow behavior
  can only be confirmed once the generator fills the template.
- **`Resume Job Title` doubles as the degree line** in Education; acceptable
  because the enclosing section disambiguates it, but a dedicated
  `Resume Degree Title` could be added if the generator needs it.
